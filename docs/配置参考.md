# 配置参考

> 全部机器相关设置都在 `runtime/config.ts`（编译产物 `lib/runtime/config.js`）：
> **内置默认 → 包内配置 → 旧用户配置 → home 配置 → `DSH_BLENDER_CONFIG` → DSH 插件设置 → 单项环境变量**，后者覆盖前者；每个生效值都记录来源（`doctor.config.sources`）。只有这一份实现；换机器只改配置，不改源码。
>
> **当前版本**：插件 **v3.1.0-alpha.1** · **6 个模型工具** · plan catalog **36 family / 239 op** · Blender 侧 addon **v2.0.0 / protocol 12** ·
> Gateway `127.0.0.1:39877` · addon 主动连接（无入站端口）。`/addon` WS 升级只接受本机回环与 `dsh-app://app` 的 Origin（无 Origin 的原生客户端照常放行，其他浏览器页面一律 403）。**唯一验收判据**：`doctor` 回 `kind=ok`。

## 1. 优先级链（高 → 低）

```text
┌ 1. 单项环境变量    DSH_BLENDER_*（见 §3；DSH_BLENDER_DNN / DSH_BLENDER_VIRTUAL_GUI 等可锁定）
├ 2. DSH 插件设置    DSH_BLENDER_PLUGIN_CONFIG（插件设置序列化后的 JSON；DNN 字段另见 §12.4）
├ 3. 显式配置文件    DSH_BLENDER_CONFIG
├ 4. home 配置文件   $DSH_HOME/dsh-blender/dsh-blender.config.json（见 §2.2）
├ 5. 旧用户配置      ~/.dsh/dsh-blender.config.json（仅兼容旧版本，可被以上各层覆盖）
├ 6. 包内配置        <包根>/dsh-blender.config.json
└ 7. 内置默认        Gateway 127.0.0.1:39877（addon 主动连接，无入站端口）· 租约 TTL 600000 ms · holder=plugin-pid-<pid> · home 见 §2.2
自动探测：home（DSH_BLENDER_HOME → $DSH_HOME/dsh-blender → ~/.dsh/dsh-blender）·
          workDir（默认 = home，见 §5）· blender.exe（macOS /Applications/Blender*.app；
          Windows Program Files / Steam；WSL /mnt/<盘>/…；再 PATH）
```

**DNN 字段的额外优先级**：保存并应用过的 DNN 字段以 `$DSH_HOME/dsh-blender/vision/runtime.json` 的当前 revision 为准（高于启动时写入的 `DSH_BLENDER_PLUGIN_CONFIG`）；`DSH_BLENDER_DNN` 只接受 `on|true|1` / `off|false|0`（大小写不敏感），命中时最高并锁定 `features.dnn`。详见 §12.4。

**怎么确认当前生效的是什么**：

```bash
curl -sS http://127.0.0.1:39877/who | python3 -m json.tool | sed -n '/"config"/,/}/p'
# 或者让模型调：blender_session(action="doctor")   → 返回里的 config 段
```

`config` 段里会写明 `configFile`（最高优先级的显式/home 配置文件，没用到就是 `null`）、`configLayers`（低 → 高的层列表）、`sources`（每个生效值的来源标签）、`home`（`path` / `source` / `requestedFrom`）、`features.dnn`（值 / 来源 / 是否被环境变量锁定）、`warnings`（弃用别名、非法插件 JSON 等）、`workDir.from`、`blenderFrom`（`config` / `auto:install` / `auto:steam` / `auto:path` / `not-found`）。

## 2. 配置文件

复制样例并改名即可生效：

```bash
cp dsh-blender.config.example.json dsh-blender.config.json
```

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `workDir` | string | home | **临时产物**目录（GUI 取帧 PNG、无头脚本、staging 等）；持久数据固定在 home（§2.2）。跨 OS 时给 **Windows 形式**（`D:\\work\\dsh-blender-rt`），WSL 下自动映射成 `/mnt/d/...`；必须"两端都能读写" |
| `blenderExe` | string | 自动 | blender 可执行文件。WSL 里给 `/mnt/d/.../blender.exe`（Windows 进程）；纯 Windows 给 `D:\\...\\blender.exe` |
| `addonHost` | string | `127.0.0.1` | 3.0.x addon 监听地址；3.1 addon 主动连接 Gateway，忽略此项（兼容保留） |
| `addonPort` | number | `9876` | 3.0.x addon 监听端口；3.1 addon 主动连接 Gateway，忽略此项（兼容保留） |
| `httpPort` | number | `39877` | 3.0.x 名称，等价于 Gateway 端口（3.1 优先用 `gatewayPort`；两台 Gateway 并存时改一台） |
| `gatewayPort` | number | `39877` | Gateway 唯一入站端口（env：`DSH_BLENDER_GATEWAY_PORT`） |
| `holder` | string | `plugin-pid-<pid>` | 写通道租约身份（多会话时便于分辨谁在写） |
| `leaseTtlMs` | number | `600000` | 租约有效期；持有者每次都续期，超时自动失效 |
| `blenderUserConfig` | string | `null` | 用户 Blender 配置目录（GPU 偏好所在）。**无头进程默认读不到它** → 想继承就设它并配合 `factory_startup=false`（env：`DSH_BLENDER_USER_CONFIG`） |
| `blenderUserScripts` | string | `null` | 用户 Blender 脚本目录（addon 所在），同上（env：`DSH_BLENDER_USER_SCRIPTS`） |
| `workerPort` | number | `9879` | 热无头 worker 的本地端口（与 Gateway 39877 区分；env：`DSH_BLENDER_WORKER_PORT`） |
| `features.virtualGui` | string | `auto`（Windows）/ `off`（Linux、macOS） | virtual-gui 能力门：`off` / `auto` / `on`。Windows V0 通过后默认 `auto`；Linux/macOS 默认 `off`，Linux 只接受显式 `on`（preview）（env：`DSH_BLENDER_VIRTUAL_GUI`） |
| `features.virtualGuiMax` | number | `4` | 同时存活的 virtual-gui 实例上限（1–16）；总内存 <16 GiB 或空闲内存 <4 GiB 时降到 2（env：`DSH_BLENDER_VIRTUAL_GUI_MAX`） |

> `features.dnn`、`vision.python/venv/model`、`vision.dnn.backend/device` 与模型目录见 §12；`cache.render.*` 见 §5.6.1。DNN 字段保存后经 `runtime.json` 热应用；`cache.render.*` 在下次 Gateway 启动生效。

### 2.1 DSH 插件配置（不是 `dsh-blender.config.json`）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `allowVirtualGui` | boolean | `false` | 是否允许 agent 启动 `virtual-gui`。默认不允许；人类可在 DSH 的 **Plugins → Blender** 配置卡或右侧栏 **Blender Presence** 面板打开开关（只影响当前 DSH 进程，不持久化），插件重载后回到这里的配置值。配置卡在启用时检测依赖：缺必需依赖先弹窗询问安装，拒绝则保持关闭；安装中显示进度；已启用后依赖被卸载会持续提示“安装或关闭”。 |

### 2.2 home 数据根与目录布局（3.2）

插件唯一的持久数据根（home）按固定顺序解析，且同一进程内只解析一次：

1. `DSH_BLENDER_HOME`（显式指定，最高）；
2. `$DSH_HOME/dsh-blender`（`DSH_HOME` 未设置时视为 `~/.dsh`）；
3. `~/.dsh/dsh-blender`。

Windows 默认 `C:/Users/<你>/.dsh/dsh-blender`，Linux/macOS 默认 `~/.dsh/dsh-blender`；`DSH_HOME` 由 DSH 宿主提供时跟随它。`doctor.config.home` 报告实际路径、来源（`env` / `dsh_home` / `default`）与 `requestedFrom`。

| 目录 | 内容 |
|---|---|
| `<home>/dsh-blender.config.json` | 可选的 home 配置（§2 同一套键） |
| `<home>/logs/` | `vision-worker.log`、`vision-install.log` 等（worker stderr 滚动保留 256 KiB） |
| `<home>/state/` | `gateway-<port>.json`、`backend-listen-error.txt` |
| `<home>/jobs/` | 作业台账 `index.jsonl` 与未显式给 `outdir` 的作业产物 |
| `<home>/sessions/` | 宿主会话记录 |
| `<home>/queue/` | `queue.json`、`staging/`（作业临时文件：`render_passes.py`、`render-config.json`、headless 脚本） |
| `<home>/cache/render/` | 渲染 pass 缓存、`index.json` 与 `.staging/`（未提升的帧目录，§5.6.1） |
| `<home>/vision/` | `runtime.json`、`runtime-state.json`、托管 `venv/`、`models/`（§12） |

- 幂等创建：在插件 `apply()` 与 Gateway 启动时创建 home 与上述子目录（**import 不建目录**），已存在的目录和用户文件**不清空、不覆盖**；创建后做一次真实写探针。
- 失败 fail closed：home 不可写返回结构化 `home_unwritable`（含路径、原因、修复建议），**不回退**到包目录或系统临时目录。`doctor` 在 `config.home.layout` 给出 `{code:"home_unwritable", path, reason, fix}`；只读 op 与只读 HTTP 面继续工作，需要写盘的子系统各自跳过自己的目录（渲染缓存禁用，队列照常渲染但不缓存）。
- 旧目录只读迁移：旧默认工作目录（Windows `%LOCALAPPDATA%\dsh-blender-rt`、macOS `~/.dsh-blender-rt`、Linux `os.tmpdir()/dsh-blender-rt`）仅在 home 目标文件**不存在**时复制 `queue.json`、`jobs/index.jsonl` 与 gateway 状态 JSON；旧目录不修改、不删除，降级仍可用。
- `DSH_BLENDER_WORKDIR` 已弃用：仍覆盖 `workDir`（临时产物目录），但不再改变持久数据根；`doctor.warnings` 会给出改用 `DSH_BLENDER_HOME` 的提示。

## 3. 环境变量

| 变量 | 等价于 | 备注 |
|---|---|---|
| `DSH_BLENDER_HOME` | home 数据根 | 最高优先；见 §2.2。相对路径按进程 cwd 解析，建议给绝对路径 |
| `DSH_HOME` | home 的父目录 | 未设 `DSH_BLENDER_HOME` 时数据根 = `$DSH_HOME/dsh-blender`；两者都未设 = `~/.dsh/dsh-blender` |
| `DSH_BLENDER_CONFIG` | 指定配置文件路径 | 配置文件层的最高优先；但低于 `DSH_BLENDER_PLUGIN_CONFIG` 与单项环境变量 |
| `DSH_BLENDER_PLUGIN_CONFIG` | DSH 插件设置（序列化 JSON） | 由 `plugin.apply()` 写入；只序列化与插件默认值不同的键，未改动的字段不会遮蔽 home 配置。DNN 字段另有 `runtime.json` 快照优先（§12.4） |
| `DSH_BLENDER_DNN` | `features.dnn` | 只接受 `on/true/1` 与 `off/false/0`（大小写不敏感）；命中时最高优先级并锁定该字段，`dnn.apply` 返回 `dnn_env_locked`。其它非空值（如 `yes`、`maybe`）被忽略：沿用配置值，doctor 报 `dnn_env_invalid` 并带原值 |
| `DSH_BLENDER_WORKDIR` | `workDir` | **已弃用**：仍覆盖临时产物目录，但不再改变持久数据根；doctor warnings 会提示迁移（§2.2） |
| `DSH_BLENDER_EXE` | `blenderExe` | 无头工具的 blender |
| `DSH_BLENDER_ADDON_HOST` / `DSH_BLENDER_ADDON_PORT` | `addonHost` / `addonPort` | |
| `DSH_BLENDER_HTTP_PORT` | `httpPort` | 后端端口（插件与后端共用同一套来源） |
| `DSH_BLENDER_HOLDER` | `holder` | 多会话时建议显式给（如 `session-A`） |
| `DSH_BLENDER_VIRTUAL_GUI` | `features.virtualGui` | `off` / `auto` / `on`；优先级高于配置文件；非法值回退 `off` 并标记 `invalid` |
| `DSH_BLENDER_VIRTUAL_GUI_MAX` | `features.virtualGuiMax` | virtual-gui 实例上限（1–16，默认 4）；低内存机器会被进一步降到 2 |
| `DSH_HIDDEN_DESKTOP_HELPER` | — | 仅 Windows virtual-gui：指定 `dsh-blender-hidden-desktop.exe` 路径（默认按 包内 `vendor/win-hidden-desktop` → 开发构建 `native/win-hidden-desktop/out` 查找）；显式指向不存在的文件时 `blender_session start` fail closed，不回退其它构建 |
| `DSH_BLENDER_LEASE_TTL_MS` | `leaseTtlMs` | |
| `DSH_BLENDER_SERVER` | — | 直接指定后端脚本路径（一般不用） |
| `DSH_HEADLESS_WAIT_MS` | — | `blender_run(action="wait")` 的客户端**等待窗口**（默认 100000 = 100 s）。到点还没跑完 → 回 `{kind:"promoted", jobId:"run-…"}`（结果不丢，用 `blender_run(action="collect", id=…)` 收）。见 §11.1 |
| `DSH_HEADLESS_AUTO_JOB_MS` | — | **自动转作业层阈值**（默认 0=关闭）：预计预算 ≥ 它的 headless 调用不等窗口，直接后台化。见 §11.1 |
| `DSH_WORKER_TTL_MS` | — | **内部 session 池空闲回收 TTL**（默认 **900000 = 15 min**；`0` = 关闭回收）。只服务 `blender_op(action="loop", target="session")` 等内部路由，不是对用户开放的会话工具；见 §5.6 |

## 4. blender.exe 怎么被找到

探测顺序（`runtime/blender-detect.ts:detectBlenderExe`；`runtime/config.ts` 只在模块加载时调用一次，不再转出该函数）：

1. `DSH_BLENDER_EXE` 环境变量；
2. 配置文件 `blenderExe`；
3. **自动扫描**：
   - Windows 官方安装：`%ProgramFiles%\\Blender Foundation\\Blender*\\blender.exe`（按目录列表顺序遍历 `Blender*`，不排序；都没有时回退到 `Blender\\blender.exe` 固定候选），来源记为 `auto:install`；
   - Windows Steam：先读注册表 `HKCU\\Software\\Valve\\Steam`（32 位安装再试 `HKLM\\SOFTWARE\\WOW6432Node\\Valve\\Steam`）的 `SteamPath`（覆盖 G:/H: 与非默认目录；读不到就跳过），再补 `%ProgramFiles%\\Steam`、`%ProgramFiles(x86)%\\Steam`、`%ProgramW6432%\\Steam`，以及 `{C,D,E,F,G,H}:\\{Program Files\\Steam, Program Files (x86)\\Steam, Steam, SteamLibrary}`（按此顺序取第一个存在的根），再读每个根的 `steamapps\\libraryfolders.vdf` 里列出的其它库，命中 `<库>\\steamapps\\common\\Blender\\blender.exe`，来源记为 `auto:steam`（vdf 缺失/损坏时只试根自身，不报错）；
   - WSL：`/mnt/{c,d,e,f}/Program Files/Blender Foundation/Blender*/blender.exe`，以及 `SteamLibrary/steamapps/common/Blender/blender.exe`、`Steam/steamapps/common/Blender/blender.exe`；
   - **macOS**：`/Applications/Blender*.app/Contents/MacOS/Blender` 与 `~/Applications/Blender*.app/Contents/MacOS/Blender`（任意版本名，如 `Blender.app`、`Blender 4.2.app`），以及挂载卷 `/Volumes/*/Applications/…`；
4. `PATH`（Windows `where blender`；Linux `which blender`）；
5. 都没有 → `config.blenderExe = null`（`blenderFrom: not-found`）：`blender_run(action="submit", kind="headless"|"render")` 立即返回 `blender_exe_missing`（含配置指引，不再抛 `TypeError`），提示三种配置方式。

**三种配置方式（任选）**：

```bash
# ① 环境变量
export DSH_BLENDER_EXE=/mnt/d/SteamLibrary/steamapps/common/Blender/blender.exe     # WSL
#   Windows: set DSH_BLENDER_EXE=D:\Program Files\Blender Foundation\Blender 5.2\blender.exe

# ② 包根配置
echo '{"blenderExe":"/mnt/d/.../blender.exe"}' > dsh-blender.config.json

# ③ 用户级配置（多个工程共用）
mkdir -p ~/.dsh && echo '{"blenderExe":"/mnt/d/.../blender.exe"}' > ~/.dsh/dsh-blender.config.json
```

## 5. 工作目录（帧 PNG 与临时产物）

持久数据（queue/jobs/sessions/logs/cache/vision）固定在 home（§2.2），**不再跟随 `workDir`**。`workDir` 现在只决定宿主与 Blender 交换的临时产物目录：GUI 取帧 live/view PNG、无头脚本、队列 staging 的用户可见副本等。

- 默认值 = home：Windows 例 `C:/Users/<你>/.dsh/dsh-blender`，Linux/macOS 例 `/home/<你>/.dsh/dsh-blender`；WSL 下默认落在 WSL 文件系统。
- **跨 OS 时必须成对**（宿主在 WSL、Blender 是 Windows 进程）：`workDir` 给 **Windows 可见**目录（如 `D:\\work\\dsh-blender-rt`），插件自动映射成 `/mnt/d/...`；不要给 WSL 内部路径（`/home/me/x`），因为 Windows Blender 只能通过 UNC 访问，而 **UNC 写入可能"成功但没有文件"**。
- 原生 Windows / macOS / Linux 同机：给本机可写目录即可；原生 Linux 不做跨 OS 映射，宿主路径原样交给 Blender。
- 别配到只读挂载（WSL 里 `/mnt/c` 通常只读，除非 Windows 侧开了对应权限）。
- 旧默认目录（Windows `%LOCALAPPDATA%\dsh-blender-rt`、macOS `~/.dsh-blender-rt`、Linux `os.tmpdir()/dsh-blender-rt`）只作为迁移来源：仅当 home 目标文件不存在时复制 `queue.json`、`jobs/index.jsonl` 与 gateway 状态 JSON，**不删除**旧目录。
- `DSH_BLENDER_WORKDIR` 是弃用别名，仍覆盖本项（临时产物），但不再改变持久数据根；见 §3 与 §2.2。

## 5.5 GPU 语义（无头渲染最贵的坑）

**问题**：无头进程（`blender -b`）**默认读不到用户偏好** → `prefs.compute_device_type = NONE`、设备列表为空 → 即使工程文件里写着 `scene.cycles.device = "GPU"`，**Cycles 也会静默跑 CPU**。
本机实测（1821 对象工程，480×270/32spp）：**CPU 2.78 s vs GPU 预热 0.18 s = 15.4×**。

**三层解法**（按推荐顺序）：

1. **默认的 `gpu:"auto"` 前导**（零配置）：按 `OPTIX→CUDA→HIP→ONEAPI→METAL` 顺序设置 `compute_device_type` + 勾选 GPU 设备 + `scene.cycles.device="GPU"`，并回传 `gpu` 字段（`before/after/configured/fell_back_to_cpu`）；
2. **`use_user_config: true`**：透传 `BLENDER_USER_CONFIG` / `BLENDER_USER_SCRIPTS`（配合 `factory_startup=false`，让无头进程继承你那套偏好与 addon）；
3. **`gpu: "true"`**：要求必须有 GPU，没有就 `ok=false`（不想再被静默降级坑一次时用）。

> 一句话：**别信文件里的 `device=GPU`，要看回执里的 `gpu.after.gpu_enabled`。**

## 5.6 后台作业、GUI 会话与长任务

| 场景 | 用什么 | 说明 |
|---|---|---|
| 一次性重活（渲染/批量几何/校验） | `blender_run(action="submit", kind="headless")` | 冷启动 0.9–1.2 s，干净、可复现；`engine="none"` 跳过前导（纯 numpy/图像任务） |
| **反复迭代 / 看画面** | `blender_py` + `blender_see` | 同一个 GUI 会话内 `K` 持久；`see=true` 同步回帧，约 50–100 ms |
| **渲染 / 相机动画** | `blender_run(action="submit", kind="render")` | 声明式参数（file/frames/resolution/samples/engine/camera），不执行脚本 |
| 单次 > 5 分钟 | 作业层 | submit 立即回 jobId；`wait`/`collect` 收日志与产物，客户端超时 ≠ 任务失败 |

**作业语义**：

- `submit` 没有同步模式；旧无头工具的 `as_job` / `wait_s` 已删除，统一用 `action="wait"` / `"collect"`。旧工具名迁移见 [MIGRATIONS.md](../MIGRATIONS.md) §0.3。
- `blender_run(action="tune", op="status"|"analyze"|"apply"|"revert")` 保留旧 Cycles 渲染分析。
- plan op 需要 ready 的 GUI 会话；catalog、dry-run、help 在本地只读执行，不需要会话。内部 session 池仅服务 `blender_op(action="loop", target="session")` 等内部路由，不是对用户开放的会话工具。

**超时/断连的语义**：客户端断开**不等于任务失败** —— 服务端子进程会继续跑完，产物仍在 `outdir`，全量日志路径在 `logs` 字段里。遇到 `fetch failed` 先翻目录。

### 5.6.1 render pass 与缓存（`cache.render.*`，3.2）

`blender_run(kind="render")` 传 `passes` 时才写每帧 manifest 并启用缓存；不传 `passes` 时既不写 manifest 也不读写缓存。

| 键 | 默认 | 允许范围 | 说明 |
|---|---|---|---|
| `cache.render.maxEntries` | `8` | 整数 1–32 | 最多保留多少条缓存（每帧一条） |
| `cache.render.maxBytes` | `4294967296`（4 GiB） | 整数 512 MiB–16 GiB | 缓存目录总字节上限；单条超过 2 GiB 一律不缓存 |
| `cache.render.ttlDays` | `7` | 整数 1–30 | 超过 N 天未被访问的条目在启动/写入清理时删除 |

插件配置写法：

```json
{ "cache": { "render": { "maxEntries": 8, "maxBytes": 4294967296, "ttlDays": 7 } } }
```

- 生效时机：Gateway 启动时读取一次，运行中改配置不改变已启动的缓存上限；**下一次 Gateway 启动**按新上限清理（TTL + LRU）。
- 非法值（非整数、越界）**不在宿主侧夹取**：原始值照样写进 `DSH_BLENDER_PLUGIN_CONFIG`；Gateway 的 `normalizeRenderCacheLimits()` 让该项按文档默认值生效，并在 `doctor.vision.cache.render.issues[]` 报一条 `{field, value, allowed, min, max, reason}`（`field` 是叶键，如 `maxEntries`；宿主侧同一份 issue 还带 `used`）。render 照常运行。
- 布局与失效：`<home>/cache/render/<sha256>/` 每帧一条，`<home>/cache/render/index.json` 用临时文件+rename 原子写；key 覆盖 scene 路径+大小+mtime、frame、camera、resolution、samples、engine、pass set 与 manifest 版本，任一变化即 miss。命中不占 GPU slot、不启动 Blender；失败/取消/不完整 manifest 不写条目；损坏条目删除后按 miss 重渲染。
- 用户指定 `outdir` 时缓存仍保留自己的副本；场景没有可 stat 的 `.blend` 路径（未保存）时不缓存。

## 5.7 virtual-gui 能力门（3.1）

3.1 的 virtual-gui 由 Gateway 拉起一个独立的 Blender GUI 并附着到 provider 提供的显示；它**不是**远程桌面，也不用于最终相机渲染。
能力门默认关闭：Windows 在 V0 验收通过并随发布打开之前为 `off`，通过后默认 `auto`；Linux/macOS 默认 `off`，Linux 只接受显式 `on`（preview，llvmpipe 仅作链路预览）。

Windows 的 W1 provider 已随 3.1 构建提供：Gateway 通过 `vendor/win-hidden-desktop/dsh-blender-hidden-desktop.exe`（开发构建在 `native/win-hidden-desktop/out/`，可用 `DSH_HIDDEN_DESKTOP_HELPER` 覆盖）启动 Blender，Blender 运行在 helper 创建的私有 desktop 上（不在默认 desktop，任务栏与 Alt-Tab 看不到），窗口保持正常显示而非最小化。helper 缺失、Blender 缺失、helper 提前退出或 ready 超时都会返回结构化错误（`helper_missing` / `blender_exe_missing` / `helper_exited` / `provider_timeout`），不回落默认 desktop；`blender_session stop` 通过 helper 的 job object 连带清理 Blender，重复 stop 幂等。

| 配置 | 行为 |
|---|---|
| `features.virtualGui=off` 或 env `DSH_BLENDER_VIRTUAL_GUI=off` | 不检测、不启动 provider；`blender_session start` 在 spawn 前返回 `stage=config` / `feature_disabled` |
| `auto` | 只在 Windows 生效；非 Windows 归 `off` 并标记 `auto-is-windows-only` |
| `on` | 显式开启；仍要求 provider 实现与全部 prerequisites 就绪，否则同样 fail closed |
| 非法值 | 回退 `off` 并标记 `invalid` |

`blender_session start`、`doctor` 与 `/status` 共用同一份 capabilities：

- `enabled` / `preview` / `ready` / `needs_approval`；
- `prerequisites[]`：每项的 `check`、`install`、`needsRoot` 与当前 `ok` / `detail`；
- `missing[]`、`reason`、`fix`：未就绪时给出可执行修法。

未就绪时启动只返回 `stage=config`（`feature_disabled` / `prerequisites_missing` / `provider_unavailable`），不 spawn Blender/Xvfb，也不静默回落 headless。Linux 的前提是 Xvfb、VirtualGL、Gateway 用户可读的 `/dev/dri/renderD*` 与 Blender；Ubuntu 22.04/24.04 与 Debian 12 的发行版仓库都没有 `virtualgl` 包（2026-11 在 packages.ubuntu.com / packages.debian.org 核对）；必须先添加 VirtualGL 官方 APT 仓库（`github.com/VirtualGL/repo`）再 `apt install virtualgl`，直接安装不是可执行步骤。WSL 不是 3.1 的目标平台。

能力就绪后，`start` 还受宿主许可门控制：插件配置 `allowVirtualGui` 默认 `false`，未获许可时工具在探测/拉起 Gateway 之前返回 `stage=session` 的 `virtual_gui_not_allowed`，不创建会话，也不会自动退回 headless 或 user-gui。人类可在 DSH 的 **Plugins → Blender** 配置卡或右侧栏 **Blender Presence** 面板打开“允许 agent 启动 virtual-gui”；开关经 DSH 认证 RPC 写入，只有已认证的浏览器人类可以改，Blender 内的 Python 拿不到该通道。运行时开关不持久化，DSH 插件重载/重启后回到 `allowVirtualGui` 的配置默认值；两个界面都显示当前连到 Gateway 的全部 GUI Blender（user-gui + virtual-gui，排除 headless），并拆分两类数量。

启动成功后的会话 id 为 `virtual-gui:<instanceId>`，只有 Gateway 拉起的那个 Blender 以同一 `instanceId` 完成 addon 握手才标记 `ready`（provider 通过 `DSHBB_INSTANCE_ID` / `DSHBB_SESSION_KIND=virtual-gui` 注入），握手超时为 30 秒；任何失败（provider 启动失败、握手超时）都会先停掉 provider，不留 Blender 进程或半注册会话。`stop` 只接受会话所有者，成功后会话与进程一起消失，重复 `stop` 返回 `stopped:false`。

同时存活的 virtual-gui 默认上限为 4（`features.virtualGuiMax` / env `DSH_BLENDER_VIRTUAL_GUI_MAX`，允许 1–16）；总内存不足 16 GiB 或空闲内存不足 4 GiB 时自动降到 2。超限时 `start` 在 spawn 前返回 `stage=session` / `capacity`，evidence 带 `used` / `limit` / `configured` / `low_resource` / `reason`；已有会话可以 stop 或复用，不会排队等待。

### 5.7.1 发行版前提与一键安装

`/doctor` 的 `virtualGui.installPlans` 是唯一安装计划来源：DSH 的 **Plugins → Blender** 配置卡、TUI 的 `doctor --fix` 与 addon 偏好设置按钮共用同一份计划。插件与扩展安装过程本身绝不运行包管理器。

| 平台 / 发行版 | 前提 | 一键安装 | 手动命令 |
|---|---|---|---|
| Windows 11 | hidden-desktop helper + Blender 4.2.10 | 无 | helper 随 3.1 包提供；缺 Blender 时设 `DSH_BLENDER_EXE` |
| Ubuntu 22.04 / 24.04、Debian 12 | `xvfb` | **是**：`pkexec apt-get install -y xvfb`（需要 polkit） | 无 pkexec 时：`sudo apt-get install -y xvfb` |
| Ubuntu 22.04 / 24.04、Debian 12 | `virtualgl`（硬件 GL；缺失只降为 preview-only） | 否 | 先加官方 APT 仓库（`github.com/VirtualGL/repo`）→ `sudo apt-get update` → `sudo apt-get install -y virtualgl`；发行版仓库没有该包，不能直接 `apt install virtualgl` |
| Ubuntu / Debian | Gateway 用户可读 `/dev/dri/renderD*` | 否 | `sudo usermod -aG video,render $USER`，然后注销重登；驱动只检测不安装 |
| Fedora | `xvfb` / `virtualgl` / `/dev/dri` | 否 | `sudo dnf install -y xorg-x11-server-Xvfb`；VirtualGL 走官方仓库，注意 `$USER` 与注销重登 |
| Arch | `xvfb` / `virtualgl` / `/dev/dri` | 否 | `sudo pacman -S --needed xorg-server-xvfb`；VirtualGL 走官方仓库 |
| macOS | provider | 无 | 3.1 不支持 virtual-gui；用 user-gui 或 blender_run(kind=render) |

一键入口有三个，都读同一份 `/doctor` 计划：

- DSH **Plugins → Blender** 配置卡：打开 virtual-gui 许可开关时先检测依赖；缺必需依赖弹窗询问是否安装。用户拒绝则许可保持关闭。安装期间弹窗保持显示“正在安装”和最近输出，完成后自动复检；仍然缺失就继续询问，不会在未就绪时打开许可。功能已经开启、之后依赖被卸载时，配置卡与 Blender Presence 面板都会显示缺依赖警告，提供“安装缺失依赖”或“关闭 virtual-gui”两个动作。一键计划以外的项显示手动命令与步骤，不伪装成自动安装。
- DSH TUI：`/blender doctor --fix` 显示缺失前提与命令；支持一键的项执行显示过的 argv（`pkexec`），完成后自动复检 capabilities。
- Blender add-on Preferences：「Virtual Display (virtual-gui)」→ **Install missing prerequisites**。只执行支持的一键命令，其余显示手动命令和原因；安装失败保留原始 stderr，且不会把 provider 标为 ready。

不装依赖就不可用：启动路径在 spawn 前检查 prerequisites，任何缺失都返回 `stage=config`（`prerequisites_missing` / `feature_disabled` / `provider_unavailable`），不启动 Xvfb/Blender，不回落 headless，也没有 force/unsafe 绕过开关。

### 5.7.2 平台限制与 preview 语义

- Windows：非管理员控制台会话已实测（5.5，32/32）；RDP 无会话环境暂不可测，锁屏会锁住用户桌面，因此不作为自动验收场景；这两项按限制记录，不算通过项。
- Linux：virtual-gui 是 **opt-in preview**，默认关闭。`vglrun`/`/dev/dri` 不满足时 provider 以 llvmpipe 启动并标 `preview-only`，不得当成硬件 GL 证据；不提供 user-gui parity 承诺；最终相机渲染一律用 `blender_run(kind="render")`，不拿 virtual-gui 当渲染机。
- WSL 不是 3.1 目标平台；WSL 的 Xvfb/D3D12 结果只作技术参考，不能替代 Linux preview 验收。

## 11. 无头作业、等待窗口与产物路径

### 11.1 等待窗口与作业语义

| 变量 | 默认 | 作用 |
|---|---|---|
| `DSH_HEADLESS_WAIT_MS` | **100000**（100 s） | `blender_run(action="wait")` 的客户端**等待窗口**。到点还没跑完 → 回 `{kind:"promoted", jobId:"run-…"}`，**结果不丢**，用 `blender_run(action="collect", id=…)` 收 |
| `DSH_HEADLESS_AUTO_JOB_MS` | **0（关闭）** | 旧版自动后台化阈值；3.1 的 `submit` 一律异步返回 jobId，此变量保留兼容 |

读取时机：两个变量都在**插件模块加载时读一次**（不是每次调用）→ **改完重启 DSH 最稳妥**。

> 语义：`submit` 立即回 jobId；`wait` 只等自己的预算，到点回 `promoted` 信封（**不是失败**）—— 服务端进程照跑、产物照落盘，用 `blender_run(action="collect", id=…)` 按 id 回收即可。

```bash
# WSL（DSH 在 WSL）
export DSH_HEADLESS_WAIT_MS=30000        # 只等 30 s，再长就直接拿 jobId 走人
export DSH_HEADLESS_AUTO_JOB_MS=120000   # 预期 >2 min 的活直接后台化

# Windows（DSH 与 Blender 同在 Windows）
set DSH_HEADLESS_WAIT_MS=30000
set DSH_HEADLESS_AUTO_JOB_MS=120000
```

**确认生效值**：`blender_session(action="doctor")` 的 `config` 段（或 `curl -sS http://127.0.0.1:39877/who`）反映后端侧生效配置；
两个 `DSH_HEADLESS_*` 是**客户端**变量，用 `node -e "console.log(process.env.DSH_HEADLESS_WAIT_MS)"` 在同一个环境里看即可。

**验收（复制即跑）**：

```python
# ① submit 立即回 jobId；wait 到点回 promoted 信封，而不是 deadline 报错
r = blender_run(action="submit", kind="headless",
                script="import time; time.sleep(200); print('HEADLESS {}')", timeout_ms=900000)
blender_run(action="wait", id=r.jobId, timeout_seconds=100)
blender_run(action="collect", id=r.jobId)      # 收日志与产物

# ② 不等待：submit 后直接拿 jobId 走人
blender_run(action="submit", kind="headless", script="print('HEADLESS {}')")
```

> 与 §5.6「客户端超时 ≠ 任务失败」的关系：这条现在**有句柄可收** —— 回执里直接给 `jobId`，不用再靠 `ls` 看 PNG 时间戳猜。

### 11.2 `outdir` / `out_json` 接受 WSL 路径

| 参数 | 当前行为 |
|---|---|
| `blender_run(kind="headless", outdir=…)` | **接受 WSL 路径**（`/home/…`、`/mnt/…`），内部用 `K.win_path` 映射；回执给真实写入路径（Windows + WSL 两种形态） |
| `blender_run(kind="headless", out_json=…)` | 同上；大结果自动溢出也落真实产物目录 |
| 脚本把 `/home/…` 交给 Windows 侧 API | 检测到就**显式报错**，不再静默漂移 |

```python
blender_run(action="submit", kind="headless",
  outdir="/home/sixtyseven67/DSH/.tmp/hull_aft",     # ✅ 直接给 WSL 路径
  script="import os, json; open(os.path.join(K.out_dir, 'probe.txt'), 'w').write('ok'); "
         "print('HEADLESS ' + json.dumps({'out': K.out_dir}))")
```

```bash
# 跑完在 WSL 侧核对（回执里也会给 Windows 形态 + WSL 可见形态两份真实路径）
ls -la /home/sixtyseven67/DSH/.tmp/hull_aft/probe.txt
```

**红线（不变）**：

- `/mnt/c|d|e|f` 是**只读挂载** —— 写不进去；
- 产物落在只读挂载 → `read_image` 打不开，每轮要多一次 `cp` 才能看图；
- **不要**往 UNC（`\\wsl.localhost\…`）写：可能"返回成功但没有文件"；
- 临时文件落**工作区**（bash 沙箱的 `/tmp` 与 fs 工具不共享，见 [操作教程.md](操作教程.md) §7.5）。

### 11.3 与 §5「工作目录」的关系

两件事，不冲突：

| | 谁的要求 | 怎么写 |
|---|---|---|
| **§5 插件 `workDir`** | 插件自身的临时产物（GUI 取帧 PNG / 无头脚本落点；Blender 侧要能直接写） | 默认 = home；跨 OS（WSL 宿主 + Windows Blender）时**必须**配 Windows 形态（`D:\…`），插件自动映射出 `/mnt/...` |
| **§11.2 调用级 `outdir` / `out_json`** | 每次调用的产物目录 | **可以直接给 WSL 路径**，映射由插件做；显式 `outdir` 的作业产物仍写该目录 |

| `vision.python` | `""` | 绝对路径或空 | 指定解释器；空 = 自动探测 3.13→3.12→3.11 |
| `vision.venv` | `""` | 绝对路径或空 | 自定义 venv；非空时插件不创建、不 pip、不回退 |
| `vision.model` | `yolov5n` | `models.yml` 顶层 key，匹配 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` | 默认预设 `yolov5n/s/m/l/x`；路径/URL 不是合法 id，`vision_detect` 传路径/URL 会返回 `vision_model_unsupported` |
| `vision.dnn.backend` | `opencv` | `opencv` / `onnxruntime` | `opencv` 只允许 CPU，不 import onnxruntime |
| `vision.dnn.device` | `cpu` | `cpu` / `auto` / `gpu` | `opencv` 与非 cpu 组合在设置校验阶段被拒绝 |

旧字段 `vision.detector` / `vision.autoInstall` **不存在**；不要按旧文档配置。

### 12.2 环境变量

| 变量 | 取值 | 作用 |
|---|---|---|
| `DSH_BLENDER_DNN` | `on` / `true` / `1` 或 `off` / `false` / `0`（大小写不敏感） | 最高优先级，锁定 `features.dnn`；配置卡开关禁用，`dnn.apply` 返回 `dnn_env_locked` 且不写快照。其它非空值（如 `yes`、`maybe`）不算锁：忽略该环境变量、沿用配置值，doctor 报 `dnn_env_invalid` 并带原值 |

### 12.3 模型目录与 `models.yml`

```text
<home>/vision/models/     # 默认 $DSH_HOME/dsh-blender/vision/models；home 见 §2.2
  GPU-DIY.md      # DNN 快捷说明（缺失时复制，不覆盖）
  coco80.txt      # 预设下载时写入
  models.yml      # 模型清单
  <subdirs>/*.onnx
```

`<home>` 未设置 `DSH_HOME` 时是 `~/.dsh/dsh-blender`；完整布局见 §2.2。`models.yml` 必填字段：`model`、`width`、`height`、`postprocessing`（本期只支持 `yolov5`）；`labels` 可选但必须非空。`model` / `labels` 必须是模型目录内相对路径，绝对路径与 `..` 逃逸会被拒绝。顶层 key 即 `vision.model`。

### 12.4 运行时快照与热应用

| 文件 | 写入方 | 读取方 | 内容 |
|---|---|---|---|
| `$DSH_HOME/dsh-blender/vision/runtime.json` | 宿主（配置卡 RPC，原子写） | Gateway | `version`、`revision`、`updatedAt`、`features.dnn`、`vision.{python,venv,model,dnn.{backend,device}}`；不含密钥 |
| `$DSH_HOME/dsh-blender/vision/runtime-state.json` | Gateway | 宿主状态展示 | `active`/`pending`/`phase`/`waitingFor`/`lastSwitchError`/`previous`/`lastStartError` |

- revision 单调：`max(现有 revision + 1, Date.now())`；同 revision 且更旧的 `updatedAt` 视为 stale。
- Gateway 在 `/doctor` 与每个 `vision_*` 请求边界 reconcile；只改 `features.dnn` 或 `vision.model` 不重启 worker。
- `vision.*` 覆盖语义：键缺省表示本层未覆盖、沿用下层；空字符串同样按“继承”处理，**不是清空**。`runtime.json` 里的 `vision.*: null` 是**显式清空**：它覆盖低层的值，让该字段回到未配置（空），不是恢复下层的旧值；在 DSH 设置里把字段清回默认值则不再序列化到 `DSH_BLENDER_PLUGIN_CONFIG`，于是自然回落 home/config 层。`vision.model` 必须匹配 `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`，路径/URL 不是合法模型 id。
- `vision.python` / `vision.venv` / `backend` / `device` 变化走两阶段：空闲立即切换；有在途请求时登记 pending，新请求返回 `dnn_config_switching`（`retryable=true`）。
- 切换失败 phase=`failed`、保留 pending、新请求返回 `dnn_config_switch_failed`；显式“取消等待”或“回滚上一版”恢复。
- Gateway 不可达：保存返回 `gateway_unreachable`、`savedForNextStart=true`、`applied=false`。

### 12.5 probe 与下载

- `dnn.probe`：一次性进程、10 秒超时、不经 shell；不写快照、不改 Gateway、不启动常驻 worker、不加载 ONNX、不联网、不安装；结果 `checks[]` 为 pass/warn/fail，`ok` = 无 fail。
- 预设下载：URL/字节数/SHA-256 固定在 `src/host/dnn-pins.ts`；单并发；`.part` → 校验 → 原子 rename；写 `coco80.txt`；`models.yml` 追加不覆盖；失败清理 `.part`；下载后无需重启 Gateway。

### 12.6 错误码

| code | stage | 含义 |
|---|---|---|
| `dnn_disabled` | config | feature 关闭 |
| `dnn_config_switching` | config | 在途请求占用 worker，稍后重试 |
| `dnn_config_switch_failed` | config | 新配置启动失败，旧 active 保留 |
| `vision_custom_env_invalid` | config | 自定义 venv 缺 cv2/numpy 或解释器不可用 |
| `dnn_backend_unavailable` | config | backend=onnxruntime 但 import 失败 |
| `dnn_device_unavailable` | config | device=gpu 但无 GPU provider |
| `dnn_no_model` | config | 模型目录没有 `.onnx` |
| `vision_model_unconfigured` / `vision_model_missing` / `vision_model_unsupported` | config | `models.yml` 条目/文件/字段非法 |
| `dnn_probe_timeout` / `dnn_probe_failed` | config | probe 超时/异常 |
| `dnn_env_locked` | config | `DSH_BLENDER_DNN` 锁定，快照未写 |
| `gateway_unreachable` | config | 配置已保存但 Gateway 未运行 |

### 12.7 Python/OpenCV 运行环境

视觉 worker 需要独立的 Python 环境；插件激活后在后台安装，不阻塞其它工具，`features.dnn` 关闭也照常安装。查找顺序：`vision.venv`（非空，最高）→ `vision.python` → `DSH_BLENDER_PYTHON` → `py -3.13/-3.12/-3.11`（Windows）或 `python3.13/3.12/3.11`（其它平台）→ `python3`/`python`；只接受 3.11–3.13 且能 `import venv` 的解释器。

| 路径（`<home>` 见 §2.2） | 用途 |
|---|---|
| `<home>/vision/venv/` | 托管 venv（先 `venv.tmp-<pid>`，校验后原子改名） |
| `<home>/vision/state.json` | 安装状态、`error`、`attempts`、`hashPolicy`、许可路径 |
| `<home>/vision/install.lock` | 单装锁（`{pid,startedAt}`，10 分钟过期） |
| `<home>/logs/vision-install.log` | 安装失败日志（阶段/退出码/stderr 尾部） |
| `<home>/vision/cache/pip/` | `PIP_CACHE_DIR`，可预热离线缓存 |
| `<home>/vision/THIRD_PARTY_NOTICES.md` | OpenCV Apache-2.0、NumPy BSD-3-Clause、Python PSF-2.0 许可声明 |

- 状态：`not_installed → resolving_python →（无系统解释器时 downloading_python）→ creating_venv → installing → verifying → ready | failed`；`vision_status.env.source` 为 `managed` 或 `custom`。
- 托管依赖固定 `opencv-python-headless==5.0.0.93` + `numpy`；`requirements.lock` 按平台固定 wheel 与 SHA-256，pip 走 `--require-hashes --only-binary=:all:`，失败最多重试 2 次（共 3 次尝试）。某平台缺哈希时降级为 `pinned-only`（`hashVerified=false`），不得报告为完整校验。
- 自定义 venv：`vision.venv` 非空时只读校验解释器/版本/`import cv2,numpy`（`backend=onnxruntime` 还要 `import onnxruntime`）；不创建 venv、不跑 pip、失败不回退，错误 `vision_custom_env_invalid` 带 `details.missingModules`。
- 离线/代理：pip 沿用 `HTTP_PROXY`/`HTTPS_PROXY`/`PIP_INDEX_URL`；完全离线且无解释器时错误 `python_missing`（托管兜底会尝试固定 URL+SHA-256 的 python-build-standalone 构建，校验失败不执行解压产物）。
- 排障：`state=failed` 看 `error.code` 与 `logPath`；锁残留且无安装进程时可删除 `install.lock` 后重试。首次安装后无需重启 Gateway，下一次视觉请求会使用新环境。
