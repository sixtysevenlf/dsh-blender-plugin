## 0. 一句话

反馈里的 P0「`blender_rt_headless` **每次都**返回 `value is not lossless JSON`、任务能交出去但收不回来」
**不是 harness 的锅，也不是非有限数**：是 v0.9.3 的 `receiptEnvelope()` 里写了一个
`promoted: ctx.mode === 'promoted' ? true : undefined` —— 宿主 `dsh-util-values` 的 lossless-JSON 门
**拒收"值为 undefined 的自有可枚举键"**（`JSON.stringify` 会把这个键**丢掉**，所以肉眼、日志、单测里都看不出来）。
一行字段写错，就把 headless 这条**第一路径**整条打死。已修 + 加中央消毒器 + 47 条回归断言（含真机）+ 启动器。

## 1. 复现与根因（可自行复跑）

1. **复现**：本会话第一次调用就是最简脚本 `print("HEADLESS " + json.dumps({"ok": true}))`，照样报
   `tool "blender_rt_headless" returned invalid output: value is not lossless JSON`
   → 说明问题**不在脚本数据**，在回执本身（headless **同步返回**也挂，不只是 job 回收）。
2. **定位**：宿主校验器 `dsh-util-values/lib/index.js → walkJsonValue()` 的规则比 `JSON.stringify` 严得多：
   - `typeof current !== 'object'` → 拒（**undefined / function / symbol**）
   - number 分支 `!Number.isFinite(current) || Object.is(current, -0)` → 拒（**NaN / ±Infinity / -0**）
   - 非普通对象原型 → 拒（Date / Map / Set / 类实例）；循环引用 → 拒
3. **命中点**：`receiptEnvelope()`（src/index.ts）那一行；而 `receiptEnvelope` 是
   **headless(sync) / headless(job 完成) / rt_job status·collect·wait** 的共同出口
   —— 与反馈里"三个工具的表现"逐条对上（op=start 不经它 ✓ 正常；op=wait/collect/status 经它 ✗ 全挂）。
4. **控制组自证**（`tests/lossless_guard.mjs` 第 3 节）：
   `{promoted: undefined}` → REJECTED；`{promoted: null}` → accepted；`NaN/Infinity/-0/Date/数组内 undefined` → REJECTED。
5. **回归测试抓到的第二处同类**：`gpu: { fell_back_to_cpu: r.gpu.fell_back_to_cpu }` —— 后端没给该字段时就是 `undefined`。
   这说明"人工避免写 undefined"是不可能的，**必须在出口收口**。

## 2. 修法（三层）

| 层 | 改动 |
|---|---|
| ① 具体字段 | envelope 改「有才给键」：`...(ctx.mode === 'promoted' ? { promoted: true } : {})` |
| ② 同类字段 | `gpu.fell_back_to_cpu: !!r.gpu.fell_back_to_cpu` |
| ③ **中央消毒器** | `vTool` 是所有工具 execute 的**唯一出口** → 出口处统一 `losslessSanitize()`：undefined→丢键（数组元素→null，长度不塌）· NaN/±Infinity→null · -0→0 · bigint→number/string · Date→ISO · Map/Set→数组 · 类实例→自有可枚举键 · 二进制→`{bytes:N}` · 循环→`[Circular]`；**每一处改动都记进 fixes 并写进回执文本**（`⚠️ 回执已消毒 N 处…`）+ `console.warn`，不静默 |
| ④ 版本自证 | `PLUGIN_VERSION` 0.9.3 → **0.9.4**（doctor 里一眼看出跑的是哪一代） |

**口径说明**：消毒器是"兜底"，不是"许可随便写"。直接写对的路径（① ②）优先，消毒器只保证
"一个字段写错不会让整条工具通道变成不可用"，并且**会把改动说出来**（避免下一轮又变成静默失效）。

## 4. 启动器：agent 自己点亮 GUI（反馈里建议的 `blender_rt_launch(autoconnect=true)`）

落地为 **`blender_viewport(op="launch")`**（能力等价，不新增第 16 个工具面）：

- **为什么不新增工具**：`doctor` / `blender-unreachable` 的"修法"现在就指向它 —— 失败点上直接可见；
  而每个工具的名字+描述+参数每次都要进 prompt，工具面能不涨就不涨。
- 语义：写 boot 脚本（GUI 里 `addon_utils.enable` 名字带 mcp 的模块 → 不行就 `importlib` 直接载入
  `$BLENDER_USER_SCRIPTS/addons/*mcp*.py` 并 `register()`）→ detached `spawn blender.exe` →
  **轮询 addon 端口**（唯一可信判据，不是"进程活着"）→ 端口开了顺手跑一次 doctor 回诊断。
- **幂等**：已在监听 → 直接 `already:true`，不堆第二个 Blender（多 agent 反复调用安全）。
- 参数：`wait_ms`（默认 90000）、`file`（要开的 .blend）、`exe`、`addon_module`、`addon_file`、`dry_run`。
- 可诊断：boot 结论落盘 `<workDir>/launch-status.json`（GUI 进程 stdout 拿不到，只能让它自己写）；
  回执给 `bootScript` 路径，人可手工复跑同一脚本。
- **自检抓到的真 bug**：`spawn` 一个不存在的 exe **不会抛**，而是异步 emit `'error'`；
  不挂 handler 会把**整个后端进程**打挂（自检第一版就是这么挂的）。已修 + 端口存在性预检。
- 依赖：`blender.exe` 走既有配置链（`DSH_BLENDER_EXE` → 配置文件 → 自动探测）。

## 4.5 追加修复：死会话的写租约自动回收（本机实测踩到）

反馈里没提这条，但**在验证过程中被它挡了一次**，而且你常开多会话 → 必然会反复踩：

- 现场：另一个 DSH 会话（holder=`plugin-pid-816309`）**进程早已不存在**，它的写租约却还在后端内存里
  继续生效到 TTL（默认 1 h，当时剩 57 min）。结果：`blender_rt_headless` 直接回
  "写通道被别的会话占用（holder=… 剩余 3513s）" —— 被一个幽灵挡在门外。
- 修法：holder 命名是 `plugin-pid-<pid>`（插件前端生成、与后端同机），后端在**写请求到达时**和
  `op=lease` 时用 `process.kill(pid, 0)` 探活；**判死即回收**，并记 `stats.staleLeasesReclaimed` +
  `lastLeaseNote`（不静默）。
- 三态语义：`holderAlive: true`（活）/ `false`（死）/ **`null`（判不了 → 按活着处理，绝不误抢）** ——
  自定义 holder（如 `orca-model-session`）属于第三类。
- 验收：`tests/lease_stale_selftest.mjs` **16 通过 / 0 失败**（独立后端，覆盖活/死/判不了三态 + 真实写路由不再 409）；
  活体验证：真后端上埋死租约 → `holderAlive:false` → 本会话 headless **不带 force 直接跑通** → `staleReclaimed:1`。
