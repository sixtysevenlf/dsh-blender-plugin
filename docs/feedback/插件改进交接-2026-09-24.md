## 1. 证据基线（本轮怎么用插件的）

- **全部工作都在 headless 完成**：没有任何 GUI Blender 会话，addon 9876 从头到尾没有 Connect（blender_viewport(op=doctor) 开局即 blender-unreachable）。
- 主力通道：`blender_rt_headless(script=/script_file=, args=, env=, engine=, timeout_ms=)`；Lead 侧长渲染用 `blender_rt_job(op=start/status/collect/list)`。
- 典型调用形态：内联 Python 做几何自检（2~5 s）；script_file 跑分件预览（110~180 s，3 视角 1024x576）；`HEADLESS {单行 JSON}` 作为结果契约。
- 单次最长任务：6 张 1920x1080 / 256 samples 渲染，总时长约 20 分钟（走 job 层）。

## 3. 缺陷清单

### D1 · headless 超时吞结果（严重 · 命中 6/7）

**现象**：内层 `timeout_ms` 与外层 run_code deadline 是两套预算；外层默认 120 s 到点后只回一行错误，没有 partial output、没有 jobId，而 Blender 端其实还在跑甚至已经跑完。

**证据原文**：
~~~
Error: code run failed (timeout): execution deadline reached (120000ms)
~~~
- hull_fore：随后 `blender_rt_job(op=list)` 显示该任务仍为 `job-muea8exqafo · running · 148042ms` —— 结果在服务端，客户端拿不到。
- cockpit：靠 `ls --time-style=+%H:%M:%S` 看 PNG 时间戳才确认「渲染其实已完成两张」。
- wings：一次 90 s 渲染的结果 JSON 全丢，被迫重跑。
- hull_aft / gear-arms / engine：同样各浪费 1 轮（gear-arms 一次丢的是面数/bbox 判据）。

**复现**：`blender_rt_headless(script_file=<3 视角预览脚本>, timeout_ms=900000)` 放进一个 **不带 timeoutMs** 的 run_code 程序（外层默认 120 s）；或任何单帧 >120 s 的脚本。

**建议修法**：
1. 客户端 deadline 到点时，若服务端 runId 仍在跑 → 返回 `{"kind":"promoted","jobId":...}`（与 bash 通道一致）并在 note 里写「用 blender_rt_job(op=collect) 收结果」。
2. 工具描述里明确写：**外层 run_code deadline 必须 > 内层 timeout_ms**，并给出推荐值。
3. 可选：headless 接受 `as_job=True, wait_s=N`（见 F-A1）。

**验收判据**：跑一个 `sleep 200` 的 headless（外层 120 s）：返回值必须含可用 jobId；后续 `op=collect` 能拿到该次 HEADLESS JSON。

### D2 · 回执是文本流而非结构化对象（严重 · 命中 5/7）

**现象**：`res.text` = 中文前言 + stdout 尾 + `result: {...}` 粘在一起，且含双层转义（`\r\n`、`\"`）。全员被迫自写正则 `result: (\{.*?\})\n` 才能取到结构化结果；`rt_job(op=collect)` 同样回大段日志，直接 JSON.parse 会抛异常。

**证据**：cockpit / hull_fore / wings / engine / gear-arms 均报告「每轮都要手写正则」；gear-arms 的 `rt_job(op=collect)` 直接 `JSON.parse` 抛异常。

**建议修法**：返回结构化字段（同时保留人类可读文本）：
~~~
{ status: "finished|script_error|timeout|promoted|killed",
  resultJson: <object|null>,      // 解析后的 HEADLESS JSON
  resultPath: <string|null>,      // 大结果落盘路径（WSL 可见）
  resultTruncated: <bool>,
  stdoutTail: <string>, stderrTail: <string>,
  runId: <string>, inputFile: {path,size,mtime,md5} }
~~~

**验收判据**：脚本 print 一行 `HEADLESS {"a":1}`，返回体必须能 `res.resultJson.a === 1`，无需正则。

### D3 · stdout 中段省略且无任何提示（严重 · 命中 4/7）

**现象**：回执把 stdout 中段替换成 `…[中间省略 N 字符]…`，把 JSON 截断；且**没有任何「请改用 out_json」的提示**（文档里有 out_json，但返回值不提）。更糟的是：末行不是合法 JSON 时，回执会变成 `_parse_error` 并**顶掉真实输出**。

**证据原文**：
~~~
…[中间省略 4028 字符]…                        (wings, 214 对象 JSON 被截断)
…[中间省略 4758 字符]…                        (reviewer, 12 次大输出探针之一)
result: {"_parse_error":"Unexpected token 'O', \"OK wrote \"… is not valid JSON","raw":"…"}   (gear-arms, 真实输出被顶掉)
~~~

**浪费**：wings 3 次往返；gear-arms 绕了 3 轮 / 8~10 分钟（最后只能写文件再读）。

**建议修法**：
1. 截断时在返回体显式给 `resultTruncated: true` + `resultPath`，并在 note 里建议 `out_json=`。
2. 末行非 JSON 时**不要**覆盖 raw：保留 stdoutTail，把解析失败降级为 note。
3. reviewer 的做法值得固化：大输出自动落盘到 `$DSH_TMP/results/run-*.json`（本轮这条救了他，但属于他自行发现）。

**验收判据**：脚本 print 30 KB JSON → 返回体必须给 resultPath 且文件内容完整；脚本 print `HEADLESS OK wrote ...`（非 JSON）→ stdoutTail 必须保留原文。

### D4 · 路径空间：WSL / Windows / C:\home 三套，且失败是静默的（严重 · 命中 4/7）

**现象 A（静默漂移）**：`script=` 内用 WSL 路径 `sys.path.insert` 能 import，但同一脚本里 `sc.render.filepath = '/home/...'` 被 Windows Blender 解释为 `C:\home\...`（日志里反斜杠还被吞），`os.path.exists()` 返回 false。

**证据原文**（hull_aft）：
~~~
日志：Saved: 'C:homesixtyseven67DSH测试建模aurorapartshull_aftqc_rear_direct.png'
紧随其后 os.path.exists() -> false；WSL bash 里也找不到该文件
~~~
**现象 B（outdir 只吃 Windows 路径）**：`outdir` / `out_json` 默认 `D:\DSH\blender\tmp`；本项目纪律禁写 D 盘，于是 wings / hull_aft / engine / gear-arms 全部改成手拼 `\\wsl.localhost\Ubuntu\...` UNC 字符串（engine 用 chr(92) 拼），而 `outdir=` 参数基本不敢用。

**现象 C（读回地狱）**：产物落在只读挂载 `/mnt/d` 时，`read_image` 打不开，每轮要额外 `cp` 到工作区才能看图（gear-arms：3 轮 × 3 视角 ≈ 6 次多余 bash）。

**建议修法**：
1. `outdir` / `out_json` / `file` 接受 WSL 路径，内部用已有的 K.win_path 映射（插件里已有该能力，只是没在这些参数上开放）。
2. 返回值里回传**真实写入路径**（Windows 形态 + WSL 可见形态各一份）。
3. 脚本运行期检测「传入 Windows API 的路径形如 /home/... 或 /mnt/...」→ **显式报错**而不是静默改写。
4. 文档明确：`/mnt/c|d|e|f` 为只读挂载，产物必须落 Windows 路径或 UNC。

**验收判据**：`blender_rt_headless(script=<写一个文件到 outdir>, outdir='/home/.../tmpout')` → 文件必须出现在该 WSL 目录且返回值给出该路径。

### D5 · 长任务不可观测：无 PYTHONUNBUFFERED、无 stage 心跳（中 · 影响全部长任务）

**现象**：job 的 stdout.log / stderr.log 在任务运行期间**全程 0 字节**（Blender 的 Python stdout 在被重定向时为块缓冲），只有进程退出才落盘。

**证据**：Lead：20 分钟渲染期间 `ls -la .../jobs/<id>/` 的两个日志始终 0 字节；engine：「399 s 那次 26 条心跳后才出末条，中间**没有任何阶段信息**（在编译着色器？建 BVH？渲染第几张？），6 分钟纯黑盒」。

**源码线索**（我 grep 到的，请复核）：`runtime/engine.mjs:966` 与 `:1089` 与 `:1572` 三处 spawn 只注入了 `PYTHONIOENCODING: 'utf-8'`，**没有 PYTHONUNBUFFERED**。

**建议修法**：
1. 三处 spawn 的 env 加 `PYTHONUNBUFFERED: '1'`（一行改动，立即见效）。
2. `op=status` 增返回 `stage` 字段：脚本可选 `print("DSH_STAGE building")` 之类的轻量契约；插件侧解析最后一条 stage。
3. 或在 job 层给出「最近一次 stdout 活动时间」与「已运行秒数」。

**验收判据**：跑一个每 2 s print 一次的脚本，运行中 `op=status` 或日志文件必须能看到增量输出。

### D6 · 作业层接口缺失（中 · 阻塞了 2 名协作者的既定建议）

**现象**：
1. `rt_job(op=start)` **不接受 `script_file` / `args` / `env`** —— 而本项目所有分件预览都靠 `args=<part>` 取参。hull_aft 原文：「回执建议我 `as_job:true` 或走 job，但 `blender_rt_job op=start` 不吃 script_file/args，无法复用靠 DSH_ARGS 取参的 preview.py」。Lead 自己也只能用「JSON 参数文件 + wrapper 脚本」绕。
2. **无阻塞等待**：cockpit 循环 `op=status` 触发外层 harness 的 `Repeated tool call detected (consecutive_calls: 5/8)`；`op=collect` 在未完成时也不阻塞。
3. **状态与实际进程脱节**：插件后端重启后 `op=status` 仍报 `running`（进程早已不存在），`op=kill` 返回 `unknown job job-...`；Lead 因此丢 ~15 分钟，最终只能用 PowerShell `Get-Process blender | Stop-Process` 清掉一个累计 798 s CPU 的孤儿进程。

**源码线索**：`runtime/engine.mjs` 的 job 启动函数内部**已经**支持 `opts.args`（`if (Array.isArray(opts.args)) args.push.apply(args, opts.args.map(String))`）→ 缺的只是 `src/index.ts` 工具面把 `args/env/script_file` 透传下去。状态对账点在同文件 `child.on('close', ...)` 与 jobs.set / ledgerAppend 附近。

**建议修法**：
1. `op=start` 增 `script_file` / `args` / `env`（与 headless 同形参）。
2. 增 `op=wait`：阻塞到完成/超时，返回结构化结果（见 D2 字段）。
3. `status/collect` 用 pid 存活对账；进程已死而状态仍 running → 立刻收敛为 finished/killed 并回传 exitCode。
4. `kill` 对未知 id 返回「已结束/不存在」而不是报错中断调用方流程。

**验收判据**：用 `script_file+args` 起一个 200 s 任务，`op=wait` 一次拿到结果；杀掉进程后 `op=status` 不再谎报 running。

### D7 · 参考图可读性：缺「读图量测」原语（中 · 让本轮返工了一整轮）

详见 **附录 A**。摘要：reviewer 为「主体掩膜 + 主体曝光统计」手搓了 3 遍（scene.ray_cast 版 / BVHTree 版 / maskdump 版），每遍都被「pixels 自下而上」与索引约定咬；Lead 侧的主体掩膜也是自写。

## 5. 结构性观察：一半工具面本轮 0 调用（需要决策）

**7/7 全未调用**：`rt_do` / `rt_see` / `rt_watch` / `blender_viewport` / `rt_cmd` / `rt_commands`。
**未调用**：`rt_worker` / `rt_loop` / `rt_perf` / `rt_opt` / `rt_txn` / `rt_preset`（属「本轮无对应需求」，非缺陷）。
**部分未调用**：`rt_plan` 的 `audit_* / qc_* / deliver_*`、`rt_job`（仅 Lead 用）。

**原因（协作者原话收敛后的三条）**：
1. **没有 GUI 会话**：9876 addon 未 Connect（doctor 开局即 unreachable），`rt_do/rt_see` 依赖主线程实时通道。
2. **并行安全**：6 路分件同时跑，动 live 场景有互相污染 + 抢主线程风险；headless 每次是干净进程（更可控）。
3. **不可用即绕过**：协作者连 `doctor` 都没跑就直接选了 headless —— 也就是说「GUI 通道路径」在并行分工场景下**默认不会被探索**。

**值得注意的浪费（不是没需求，而是不知道该用）**：
- hull_fore 手写 ~60 行「世界顶点哈希重复组 + AABB 浮空」检测 → 对应 `audit_duplicates` / `audit_snap_floaters`。
- hull_aft 手写 BVH 最近距离浮空扫描 → 对应 `audit_*`。
- reviewer 手搓 3 遍主体掩膜统计 → 对应 `qc_subject_mask`（见 F7）。
- **他们都提到同一个原因**：这些 op 在描述里没有「传集合名、逐件出报告」的可抄示例，且不确定能否脱离 addon 在 headless 直调。

**建议**：
1. 把纯 bpy 的 `audit_* / qc_*` 明确标注「可在 headless 直调」，并各附一段 copy-paste 示例（含 `coll=` / `file=` 参数形态）。
2. 若 GUI 通道希望进入并行分工流程，需要在任务模板/文档里显式写「本任务是否要求 GUI + Connect」；否则默认走 headless。
3. 建议内部把「无头批处理」定为**第一路径**，「直连 GUI」为交互式增益 —— 本轮的证据是 7/7 全选 headless。

3. **D3**：print 30 KB JSON → 有 `resultTruncated:true` + `resultPath`，文件完整；print 非 JSON 末行 → stdoutTail 保留原文。
4. **D4**：`outdir='/home/.../tmpout'` → 文件落在该 WSL 目录且返回值给出该路径；脚本向 Windows API 传 `/home/...` → **显式报错**。
5. **D5**：每 2 s print 的脚本 → 运行中可见增量输出（或 `op=status.stage` 变化）。
6. **D6**：`script_file+args` 起 200 s 任务 → `op=wait` 一次拿结果；kill 进程后 `op=status` 不再谎报 running；`op=kill` 对未知 id 不抛错。
7. **F1**：`shots=[3 个视角]` → 回 3 条 {name,path,ms,md5,coverage_estimate}，且主体占比 <5% 时出 warning。
8. **F6**：`file=<blend>` → 返回体带该文件的 size/mtime/md5。

## 附录 A · 第二类问题：参考图「读图量测」

### A.1 现象（本轮的核心质量瓶颈，不是插件的锅，但插件可以补工具）

- 参考源全是**官方 3/4 透视美图**（3436×2160 / 4.6 MB），没有正交三视图。
- 母图被统一**降采样到 1500 px** 再分发：约 55 px/m，0.1 m 板缝 ≈ 5 px、0.05 m 铆钉 ≈ 2 px → 等于不可读；原生分辨率约 **126 px/m**（缝 12.6 px）。
- 站位表（机头 9.5 / 盖顶 6.45 / 引擎环 2.15…）是 Lead **目测**填的，却被写成冻结契约；6 路分件据此对齐 → 错误自洽（装配完美、整体偏离真船）。
- **零量化校验**：没有任何「正交渲染 vs 参考图」的剪影 IoU/边缘叠加；复审的 V1 座舱盖格架、V3 机头蛋形、V4 机翼零厚度都是成图后才发现。

### A.2 建议补的三个工具 + 一段文档

| 项 | 请求 | 建议签名 |
|---|---|---|
| T-A1 | **参考图量测** | `ref_measure(image, p1, p2, known_len_m, out_grid_png)` → 回 `{px_per_m, stations:[{px_x, metres, err_m}], grid_png}` |
| T-A2 | **原生分辨率特征图册** | `ref_crop_atlas(image, crops=[{name, box_px}], outdir)` → 批量出**不缩放**裁剪 + `atlas.json`（源图/裁剪框/px-m/换算尺寸/md5） |
| T-A3 | **可读性体检** | `ref_readability(atlas_json, min_px=8)` → 列出「图上不可读」的特征，逼调用方换更近的来源或标记为未知 |
| T-A4 | **文档** | `docs/证据分级与读图纪律.md` 增「读图量测」节：禁用量测自缩图；量测必须带 provenance 与误差；<0.3 m 特征必须有原生裁剪；透视图的 X 向站位一律标「近似」 |
| T-A5 | **剪影对拍（已有能力，缺示例）** | 把 `rt_plan(op='qc_compare')`（IoU/Dice/缺面积/边界距离 + 三联对照）的示例补进描述，并注明可 headless 直调 |

### A.3 流程建议（如果插件要管流程）

把「阶段 1 白模与比例锁定」设为硬关卡：入口条件 = 带误差的站位表 + 特征裁剪图册 + 剪影 IoU 达标；不达标不派分件任务。本轮等于是跳过了比例锁定直接进细节还原，所以「每块板都倒角、每颗铆钉都算面数」的工程投入全花在了错误的轮廓上。
