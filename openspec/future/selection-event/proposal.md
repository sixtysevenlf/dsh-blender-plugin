# Proposal — SelectionEvent envelope (parked)

> Parked future work. This is not an active OpenSpec change and must not be implemented from `openspec/future/`.
> It depends on `gateway-topology-3-1` and `asset-library-v1`; move it to `openspec/changes/` only when the work starts.

## Why

Blender → DSH selection currently has four hard-coded layers:

- addon `commands/selection.py` builds `objects` / `collection` payloads and posts them;
- host `/host/selection` sanitizes a `SanitizedSelection` whose `kind` only allows those two values;
- TUI `src/tui/selection.ts` formats the payload into draft text and a chip;
- Web `src/client/index.js` repeats the same formatting and insertion logic.

`asset-library-v1` adds a third `kind=asset` directly. Future Blender → DSH actions — line-guided retopology, curve guides, material or scene snippets, reference boards — would each add another kind and another copy of the same four branches. The addon, host sanitizer, TUI, and Web client would drift independently.

A thin envelope is enough: the transport route stays the same, but each kind carries a stable title, draft text, and bounded structured data.

## What Changes

- Define a versioned `SelectionEvent` envelope:
  - `v`, `kind`, `title`, `draft_text`, `data`, optional `scene`, `activity`;
  - `kind` is an open string with per-kind validators, not a closed union in the transport.
- Addon: one builder per kind, one `_post_selection_payload(event)`; keep `objects` / `collection` / `asset` compatible while the clients migrate.
- Host: generic length/security limits; per-kind data validator; keep `latest` / `consume` CAS semantics.
- TUI/Web: prefer `title` and `draft_text`; keep a legacy formatter for old payloads until the migration is complete.
- Add a future `retopo_guide` kind as the first new proof: curve points / guide file reference, no automatic import.
- Do not add an HTTP route, model tool, or addon wire command.

## Capabilities

### New Capabilities

- `blender/selection-events`: versioned Blender → DSH selection envelope with per-kind validation, bounded data, and stable draft text.

### Modified Capabilities

- `blender/asset-library`: asset selection uses the envelope while preserving the existing `/host/selection` route and 1–20 refs limit.

## Impact

- **Extension**: `commands/selection.py`, asset-browser panel/operator, future guide operator; no command-count change.
- **Gateway/host**: `runtime/selectionstore.ts`, `runtime/http/host/routes.ts`; route count unchanged.
- **Clients**: `src/tui/selection.ts`, `src/client/index.js`; one shared textual path.
- **Compatibility**: old `objects` / `collection` payloads remain accepted; no wire-protocol bump.
- **Tests**: fixture payloads for each kind, over-limit rejection, legacy compatibility, TUI/Web parity.
- **Non-goals**: implementing line-guided retopology itself, replacing the selection store, adding a new transport, or changing model tool count.

## Open Questions

- Does `data` need a schema registry, or are per-kind validators in host sufficient?
- Should `draft_text` be generated by addon or host? Addon has Blender context; host has final session wording. Prefer addon with host fallback.
- How large may a guide payload be before it becomes a file reference instead of inline data?
- Do we keep the legacy `objects` / `collection` fields indefinitely, or migrate them to envelope-only after one release?
